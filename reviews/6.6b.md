# Review — 6.6b Claude usage without extra endpoint calls (v0.3.1)

- **Trigger:** Kevin: "the usage endpoint does have rate-limiting, so we should try to throttle our calls to it"; then
  "piggyback on ccstatusline's values so that the usage endpoint only needs to get called once".
- **Change:**
  - ccstatusline's own cache (`~/.cache/ccstatusline/usage.json`: 5h, weekly and Fable with reset times, plus only a
    token hash) is now the **primary Claude source**. It costs zero endpoint calls, reads no credentials, and takes
    its freshness from the file mtime.
  - The chain is: ccstatusline cache → throttled usage endpoint (opt-in) → statusline tap.
  - The endpoint throttle matches ccstatusline:
    - at most one call per 5 minutes per profile, through a shared cache file that holds numbers only;
    - on a 429, wait for Retry-After (else 5 minutes);
    - errors are reused for 60s.
- **Live:** ccstatusline's cache on Kevin's machine read 5h 7%, weekly 21%, Fable 22%, with resets.
- **Tests:**
  - the mapping, skipping zero placeholders;
  - provider errors;
  - the chain, where only the tap is flagged as a reduced fallback;
  - the throttle: interval, cross-instance sharing, Retry-After back-off and error reuse.

  Tests use memory-only throttling so they never write to the real home folder. The first run did write there; the
  stray files were removed. 272/272.
- **Review:** a small follow-up on 6.6's reviewed code; cross-review requested from Astra.

- **Astra's cross-review: HOLD, 4 findings, all fixed:**
  1. Global-cache attribution: the ccstatusline cache is used only for the default Claude profile and labelled 'ccstatusline cache (default Claude login)'.
  2. Freshness: source selection now prefers the first FRESH reading, so an old cache no longer blocks a fresher source; the stale one is kept only when nothing fresher works.
  3. Shape: null/array/primitive JSON is handled without throwing, and a fixed diagnostic replaces the cache's error text.
  4. Endpoint exclusion: in-process single-flight plus an exclusive reservation file (abandoned after 30s). The guarantee is narrowed to 'best effort' in the docs.
  - Optional mapping fix applied: Fable 0% counts as a reading; Sonnet/Opus 0 without a reset is a placeholder.
  - Tests: 273/273, nothing written to the real home folder.

- **Astra's re-review (of d09d416): HOLD, 3 findings, all fixed:**
  1. Attribution: the cache is never called the "default Claude login". Its source is 'shared ccstatusline cache (login unverified)', and it has an opaque identity: `key` is a re-hash of ccstatusline's tokenHash, and a read failure keeps the last seen identity. `scope` stays 'profile', because a token hash is not a verified account id. `sourceKey` stays the per-profile key, so the top bar keeps one Claude row whichever source serves it.
  2. Fallback flag: the tap is flagged as a reduced fallback whenever it stands in for a fuller source tried first, including a fresh tap replacing an old-but-ok cache. There's a regression test.
  3. Reservation:
     - the lock holds `{at, nonce}`;
     - an empty or invalid lock is held while its mtime is recent;
     - an abandoned lock is taken over only if it's unchanged since it was judged stale;
     - release unlinks only our own nonce;
     - the cache is re-read under the reservation before fetching.

     Tests cover the empty/fresh lock, the empty/old takeover, and a foreign lock surviving our release.
  - 274/274.

- **Astra's second re-review (of 09de35f): reservation and labelling accepted. 2 integration blockers, fixed and tested through AccountMonitor:**
  - **A)** A fresh tap that stands in for a fuller source now carries every model limit the chain has seen (e.g. Fable) as an explicit `n/a` window ("the statusline tap does not report model-specific limits"). The tap and cache logins can't be matched, so old values are never kept.
  - **B)** Identity:
    - the cache's `key` is its hashed token only when a `tokenHash` is present, else the profile key (no identity), so a reading is never stamped with a prior login;
    - `AccountMonitor.merge` drops the last good reading when a sample is positively identified (`scope=account`, or `key ≠ sourceKey`, a convention documented in the contract) and names a different login;
    - read failures (no identity) still keep the last reading as stale.
  - The top bar shows "(ccstatusline, login unverified)".
