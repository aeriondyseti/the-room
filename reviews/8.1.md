# Review — 8.1 Ghost cleanup (Milestone 8: participant lifecycle)

- **Scope:** `git diff 8fb35f7...sprint/8.1` — `src/core/service/service.ts` (registry-driven `participants()` that
  prunes departed ledger rows and is the only emitter of `participant.removed`; `syncDisplay` replacing both stale
  publishing loops; startup `reconcile()`; async `start()`), `src/core/ledger/ledger.ts` (`relabelQueued`; withdraw
  resolves current delivery rows), `src/ipc/server.ts` (awaits `start()`), `src/core/service/participants.test.ts`.
  Spec: docs/PARTICIPANT-LIFECYCLE-SPEC.md §1–2.
- **Why:** two manual renames on 2026-09-28 left ghost handles in the TUI. `who` was clean (registry-driven), but
  the inbox-display refresh and the withdraw pending loop walked the ledger's name-keyed participant table and
  republished the stale rows, and nothing ever emitted `participant.removed`. Diagnosed by opus (#429), verified.
- **Lean review, run 1 (ADR-0007; 2 reviewers + 1 batched verifier):** complete, no failures, none unresolved.
  - **Actionable, all fixed:**
    1. A relabelled delivery could not be withdrawn: withdraw derived its targets from the message's historical `to`
       list. It now resolves the message's current delivery rows (in the message's own order, plus rows relabelled to
       a name the message never listed); an explicit old name is refused with the current list. Test added.
    2. Pruning from a per-request registry snapshot raced a concurrent `join`: the new row was deleted and announced
       removed. `syncDisplay` now always uses a fresh registry read (`participants()` reads for itself).
    3. Withdraw did not recompute pending (the flag was never passed). Fixed; test asserts the stored and published
       count.
    4. A failing reconcile aborted service startup. It is now caught and reported on stderr; the dispatcher's own
       registry checks cover such deliveries as before.
  - **Tech debt fixed anyway:** a relabelled stop request was held under pause (now never); `relabelQueued` rules
    tested (queued-only via a withdrawn row; held follows pause); feature labels corrected to 8.1; main merged so the
    spec the Done-when cites exists on the branch.
  - **Deferred:** TD-0040 (a primary-key collision leaves a row stranded under the departed name; reconcile now
    reports it instead of claiming a full repair; 8.2's explicit rename refuses such a case).
- **Astra's early cross-look (#456, #457):** the collision report above, and the self-rename notice split (spec §3,
  §7), both adopted.
- **Tests:** `participants.test.ts`, 11 tests: rename then who/inbox/send/withdraw never resurrect the old name;
  announced once; rebound name superseded not removed; a TUI rebuilt from `who` plus events never shows the departed
  name; reconcile relabels (same target, stale rebind wait cleared), is idempotent, leaves an orphaned binding alone;
  withdraw after relabel; withdraw recomputes pending; pause vs stop request; withdrawn rows keep the old label.
  `npm test`: 489/489.
- **Lean review, run 2** (base 65a05b1): complete, no failures, none unresolved.
  - **Actionable (fixed):** `syncDisplay` took its ledger snapshot before awaiting the registry read and wrote those
    rows back afterwards, so a monitor or dispatcher write during the read (liveness, usage, pending) was clobbered
    and republished stale. The snapshot is now taken after the await, making the read-modify-write synchronous.
  - **Tech debt fixed:** the stranded-row report ran once per queued row and counted crashed in-flight rows as
    collisions (now once per departed name and binding, in-flight rows excluded); the two untested Done-when items
    (collision report, reconcile failure never aborting `start()`) now have tests.
  - **Deferred:** TD-0041 (`relabelQueued` against a live worker that has selected but not yet claimed a row; unreachable
    in 8.1, which runs it before the dispatcher starts; 8.2's live rename must quiesce or tolerate it).
- **Astra's cross-review (#462):** the display refresh after a committed send ran before the message event, the
  dispatcher kick and the response, so a failed registry read could report an error for a persisted send. Fixed:
  every request announces its outcome and kicks delivery first, then refreshes the display best-effort
  (`refreshDisplay`, caught and reported on stderr).
- **Final:** `npm test` 491/491 (see the commit).
