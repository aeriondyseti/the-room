# 006.02 Background agents: the TUI as the single point of control

## Scope

Raised 2026-09-28 by Kevin. Agents run backgrounded, with no terminal UI of their own. The room TUI becomes the one
place to watch, direct and control every connected agent.

What it would pull forward (each agent's own terminal covers these today):

| Need | Why | Candidate mechanism |
| --- | --- | --- |
| Seeing the work | With no terminals, a messages-only view leaves Kevin blind to tool calls | The transcript observer (the activity view, task 6.1) becomes required |
| Permission prompts | No pane to answer them, so the agent stalls | Pre-approved policies (allowlists, auto modes) or passing approvals through the TUI |
| Hard stop | Pause is only a request, and there's no Esc key | `claude stop`; Codex `turn/interrupt` through the app-server |
| Lifecycle | Current scope is "attach only, never launch" | The room would start and stop agents, which reverses that decision |

Design guidance meanwhile (no commitment): keep the delivery adapters independent of how the agent is hosted (don't
assume a TUI is attached), so this remains possible.

### Check results (2026-09-28, while the idea was parked)

All checks used throwaway sessions and threads. Details: `attachments/claude-background-results.md` and
`attachments/codex-background-results.md` (runner `probes/codex-background-check.mjs`).

| Capability, with no TUI | Claude Code 2.1.283 (`--bg`) | Codex 0.157.1 (app-server daemon) |
| --- | --- | --- |
| Host the agent | ✅ `claude --bg -n <name>` | ✅ daemon `thread/start`, or adopt with `thread/resume` |
| Wake on a message | ✅ pipe message | ✅ `codex queue` consumed while idle (about 0.2 s to turn start); busy → next turn |
| Watch the work | ✅ live transcript JSONL; registry `status`/`waitingFor`; `claude agents --json` | ✅ rollout JSONL grows with tool calls, results, tokens and interruptions |
| Approve a permission prompt | ❌ only through `claude attach` or agent view; a priority `now` message *denies* it | ✅ the approval request reaches subscribed app-server clients and survives disconnects (replayed on reconnect); cancel verified, **grant not tested** |
| Soft interrupt (keep the session) | ❌ no external path | ✅ `turn/interrupt` cancelled a running turn in about 0.2 s; the thread resumes |
| Hard stop | ✅ `claude stop <id>` in under 1 s; resumes on the same id | (`turn/interrupt` suffices) |
| Headless per-message fallback | — | `codex exec resume` keeps the id when the thread is unowned, but **fails** when the daemon or a TUI holds it |

Takeaways:
- Codex is the more controllable background harness: approvals and soft interrupt both go through its app-server.
- Claude's gap is approvals. Pre-scope permissions (`--allowedTools` / `--permission-mode`) or hand off to
  `claude attach` when `waitingFor` shows a prompt.
- Untested: long-idle expiry, daemon restart, the documented 30-minute unload grace, and repeated-trial
  reliability.

What was known before the checks: a pipe message wakes a `--bg` Claude session, and the Claude participant in this
project was itself a background session driven by messages
(`git show v0.9.0:findings-claude-messaging.md`). `codex queue` items only ran once a TUI had the thread loaded
(`git show v0.9.0:findings-codex-messaging.md`); a guaranteed but less elegant fallback is `codex exec resume
<thread> "<message>"`, serialized, one per message, for background-only agents.

Checks still to run if pursued:
1. Codex: does a daemon-hosted thread consume `codex queue` items on its own, and how do you move a thread onto the
   daemon (or background it)?
2. Claude: what happens to a permission prompt in a `--bg` session?
3. Hard stop: `claude stop` and Codex `turn/interrupt`, including the effect on the session's resumability.
4. Observation: transcript tailing for background sessions of both harnesses.
